# preinstantiate
<!-- cargo-sync-rdme ]] -->
<!-- cargo-sync-rdme rustdoc [[ -->
`preinstantiate` makes one crate compile the `pub async fn` bodies of
another crate, so that downstream crates don’t have to compile those bodies
themselves.

In [Omicron](https://github.com/oxidecomputer/omicron), after an edit to a
`nexus-db-queries` method, rebuilding `omicron-nexus` goes from around 25
seconds to around 11. (This was measured with Rust 1.99.1 on a computer with
an AMD Ryzen 9 7950X processor running Linux.)

## Motivation

Let’s say `nexus-db-queries` has a method like this:

````rust,ignore
impl DataStore {
    pub async fn silo_delete(&self, id: SiloId) -> Result<(), Error> {
        // ...
    }
}
````

You might ordinarily expect the compile process for `nexus-db-queries` to
generate code for the body of `silo_delete`. But in reality it is treated as
*monomorphized*, similar to a generic function. With monomorphized
functions, only higher-level instructions for how to compile code are
generated, and the actual code is only generated when the function is
instantiated with specific types.

<details>

<summary>Why is this the case?</summary>

A function like `silo_delete` isn’t actually generic. Why does it need to be
monomorphized?

This looks like a little bit of an accident! In Rust 1.100, treating
functions as monomorphized like this is restricted to `pub async` functions
associated with a type, like `DataStore::silo_delete`. It does not apply to
`pub async` module-level (free) functions, which *are* generated at the
place they’re defined. Based on [rust-lang/rust#143290] this doesn’t
seem intentional, at least at first glance; someone in the Rust community
could reasonably notice and fix this, making `preinstantiate` moot. So this
crate has a bit of a fleeting nature. C’est la vie.

</details>

Anyway, accepting that this is the case, the code for this function is
generated at the call site in `omicron-nexus`, not within
`nexus-db-queries`. In Omicron’s case this adds up a lot of code, all of
which is generated towards the end of the build process within
`omicron-nexus`.

````mermaid
flowchart RL
    store["nexus-db-queries<br/>defines DataStore's<br/>async methods"]
    mid["about 10 intermediate crates"]
    nexus["omicron-nexus<br/>compiles every method body<br/>(741 futures)"]
    nexus --> mid --> store
    nexus --> store
    style nexus stroke-width:3px
````

The Rust compiler has an option called *share-generics* which helps here.
When this option is enabled, downstream crates can reuse monomorphized code
generated by upstream crates. In Rust 1.100, share-generics is enabled for
dev builds but not release builds[^opt-level].

With share-generics, if some crate upstream of `omicron-nexus` generates
code for `silo_delete`, `omicron-nexus` can use it. `preinstantiate` is a
way to set up that scenario above. (The name comes from [explicit template
instantiation][explicit template instantiation], which solves a similar problem in C++.)

### Why separate crates?

We could force code generation within `nexus-db-queries`. But when
share-generics is on, rustc can’t write out a crate’s metadata until it has
worked out which monomorphized functions will be exported by it. Downstream
crates cannot start compiling until this metadata has been written out. In
Omicron, same-crate preinstantiation was observed to cause builds to be
10-15% slower.

So instead of being in the same crate, `preinstantiate` forces code
generation within a few *shard* crates. (Each source file is assigned to a
shard by hash.) Each shard depends only on the upstream crate, so shards
can build in parallel with each other.


## Usage

We call `nexus-db-queries` the upstream crate, and the downstream crate such
as `omicron-nexus` the downstream crate.

First, for each shard, create a crate that depends on the upstream crate and
on `preinstantiate`. Turn on the `build` feature for the build script:

````toml
[dependencies]
nexus-db-queries.workspace = true
preinstantiate.workspace = true

[build-dependencies]
preinstantiate = { workspace = true, features = ["build"] }
````

In each shard’s build script, define the source files to do analysis on:

````rust,ignore
use preinstantiate::build::{Config, ShardIndex, run_build_script_or_exit};

fn main() {
    let shard = ShardIndex::new(0, 8).expect("shard 0 of 8 is valid");
    let config = Config::new("../nexus-db-queries/src/lib.rs", shard)
        .add_async_inherent_methods("nexus_db_queries::db::DataStore");
    run_build_script_or_exit(&config);
}
````

`preinstantiate` will do a source analysis to find `pub async` methods
defined on `DataStore` filtered to that shard, and write out a function
which forces code for that shard to be generated. In the shard’s `lib.rs`,
include it:

````rust,ignore
include!(concat!(env!("OUT_DIR"), "/preinstantiate_async_fns.rs"));

use nexus_db_queries as _;
use preinstantiate as _;
````

(The `use` statements are required by Rust 1.100’s unused dependencies
lint.)

Finally, in the downstream crate, add dependencies and `use` statements for
all the shard crates:

````rust,ignore
use nexus_db_queries_preinstantiate_0 as _;
use nexus_db_queries_preinstantiate_1 as _;
````

For a working example, see [`e2e-example`].

### Analysis limits

`preinstantiate` does a source-level analysis of the upstream crate. We are
conservative and skip over methods that:

* Are generic over types or consts (lifetimes are fine).
* Accept an `impl Trait` argument.
* Are `unsafe`.
* Have a `cfg` or `cfg_attr` attribute, or are inside an `impl` block
  gated that way.
* Are in a module declared with `#[path]`.
* Accept more than [`MAX_ARITY`] arguments, including `self`.

We don’t have to be perfect to realize the build time improvements — it is
sufficient to instantiate the vast majority of async functions.

### Debugging

To check whether `preinstantiate` is working as expected, pick a method and
compare how many copies of it are compiled with share-generics on
and off:

````console
$ cargo rustc -p omicron-nexus --lib -- -Zprint-mono-items=yes \
    | grep -c 'DataStore>::silo_delete'
$ cargo rustc -p omicron-nexus --lib -- \
    -Zprint-mono-items=yes -Zshare-generics=no \
    | grep -c 'DataStore>::silo_delete'
````

The two numbers should be relatively far from each other. If they are close
to each other, `preinstantiate` is not working or not providing any benefit.

The build script writes a report to
`OUT_DIR/preinstantiate_async_fns-report.txt` with information about
included and skipped methods.

### Release builds

If share-generics is off, the preinstantiate scheme doesn’t work. With
current versions of Rust, share-generics is off in release builds, so
`preinstantiate` disables itself.

[^opt-level]: More specifically, `share-generics` are enabled under
    opt-level 0, 1, `s`, and `z`, but not 2 or 3.
